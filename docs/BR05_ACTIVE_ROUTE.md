# BR-05 · 안내 요청 전 활성 경로 조회

폰에서 미리 보낸 경로는 차량 앱이 열린 뒤 자동 시작한다는 결정을 유지한다. 시동만으로 앱이 열리는지는 공개 근거가 없어 미검증이다. 영상에서는 운전자가 앱을 열고, 폰 전송 뒤 자동 안내 요청은 **구현 목표**로 표시한다. [BR-15 결정 기록](BR15_STARTUP_20261105.md)

늘길은 기존 안내를 확인하고 사용자에게 현재 상태를 보여 준다. 조회만 하면 세 경우 모두 발행은 0회다. 아래는 목적지가 준비되고 정차한 한 이동에서 안내 시작을 시도했을 때의 모의 내비 발행 횟수다.

| 조회 결과 | 확인 가능 조건 또는 화면 상태 | 모의 경로 요청 |
|---|---|---:|
| ACTIVE | ALREADY_GUIDING · 이미 안내 중. 기존 안내 유지 | 0회 |
| INACTIVE | 목적지 준비·정차 확인 후 READY. 최신 응답에서 `canConfirm`이 참일 때만 발행 | 1회 |
| UNAVAILABLE | ROUTE_UNAVAILABLE · 현재 경로 조회 불가. 다시 조회 가능 | 0회 |

## 상태를 읽고 발행하는 순서

1. Android는 연결 및 화면 복귀 시 상태를 조회한다. 조회하는 동안 확인 버튼을 잠근다. 활성 경로가 보이면 요청을 보내기에 앞서 기존 안내를 표시한다.
2. 폰에서 보낸 경로는 폰 전송을 운전자 확인으로 본다. 차량 앱이 열린 뒤 취소할 시간이 지나면, 같은 경로가 여전히 유효한지 확인하고 요청 직전에 `refreshActiveRoute()`를 호출한다. 새 응답의 `navigation.canConfirm`이 참일 때만 해당 이동의 `confirm()`을 한 번 보낸다. 취소·경로 교체·조회 실패·정차 미확인 때는 보내지 않는다. 폰에서 보내지 않은 날은 차량 화면에서 운전자가 직접 확인한다. 순정 어댑터는 발행 직전에도 경로·정차·장소·발행 기록을 검사한다.
3. 게이트웨이가 미발행을 확정한 경우 이유를 반환한다. 실제 발행 뒤 응답 유실·검증 실패는 UNCONFIRMED로 남긴다. 완료·미확인 이동은 현재 상태를 다시 읽어도 발행 잠금을 유지한다. 조회·화면 복귀·응답 유실에 따른 자동 재전송은 0회다.

현재 구현은 앱의 관측 시점까지 확인한다. 순정 서비스가 조회와 요청을 원자적으로 처리하는지, 실제 차량에서 상태와 콜백이 어떤 순서로 오는지는 기기 시험 대상이다.

## 클라이언트 연결

- `navigation.activeRoute`는 ACTIVE, INACTIVE, UNAVAILABLE 중 하나다. `navigation.state`는 늘길의 요청 진행 상태다. 확인 버튼은 `navigation.canConfirm`과 새 계약의 INACTIVE 여부를 함께 본다. 이전 1.0 서버에서 필드가 없으면 BR-05 지원 서버로 갱신한다.
- `await api.refreshActiveRoute()`는 게이트웨이를 조회하고 전체 상태를 반환한다. `getState()`는 마지막 관측을 읽는다. 둘 다 내비에 경로를 요청하지 않는다.
- 모의 시나리오는 `api.setDemoScenario({ activeRoute: "ACTIVE" })`로 설정한다. 새 이동에서 활성 또는 조회 불가 상태로 confirm을 직접 호출해도 HTTP 409와 각각 ALREADY_GUIDING, ROUTE_UNAVAILABLE 코드를 받는다.
- 일반 안내 성공(VERIFIED)과 발행 후 미확인(UNCONFIRMED)은 마지막 요청 결과다. 같은 이동의 재확인은 TRIP_LOCKED로 차단한다. 모의 시연을 다시 시작할 때만 newDemoTrip을 사용한다.
- `codex/frontend-design`의 `3199362` 웹 시연은 폰에서 미리 보낸 경우의 재조회와 조건부 확인을 모의 연결로 재현한다. BR-02 Android의 현재 진입 경로는 차량 화면의 수동 확인이며, 실제 폰 수신과 자동 요청은 구현 목표다.
