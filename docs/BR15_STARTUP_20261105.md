# BR-15 · 시동 후 늘길 실행과 순정 경로 복원

조사일: 2026-11-05 (한국 시간) · 대상: 일반 설치형 Pleos Connect 차량 앱, 늘길의 target SDK 34 / NaviHelper 3.0.5. 문서·소스 조사이며 차량 시험 성적서가 아니다.

**판정:** 운전자가 늘길을 열었을 때 앱이 저장된 규칙을 읽어 오늘의 목적지를 제안하는 방식은 공개 플랫폼 모델에 맞는다. 반면 시동마다 종료된 늘길이 스스로 전면에 열리거나, 늘길이 열리기 전에 지난 순정 경로를 그대로 살릴 수 있다는 공개 계약은 확인하지 못했다. OEM의 기본 앱 동작이나 특정 차종의 마지막 화면 복귀까지 불가능하다는 결론은 아니다.

## 어느 동작까지 말할 수 있나

| 운전자가 보는 동작 | 근거와 판정 |
|---|---|
| 시동만 걸면 늘길이 매번 열린다 | PT의 보장 동작으로 채택할 근거 없음. [Android의 화면 실행 정책](https://developer.android.com/guide/components/activities/secure-bal)은 백그라운드 앱의 전면 실행을 제한하고 사용자 런처 탭 같은 예외를 구분한다. [부팅 완료 방송](https://developer.android.com/reference/android/content/Intent#ACTION_BOOT_COMPLETED)은 OS 부팅 후 초기화용이다. [AAOS 전원 모델](https://source.android.com/docs/automotive/power/power)에는 차 문을 열 때 절전 상태에서 복귀하는 경로도 있다. 시동·탑승·새 OS 부팅을 동일 이벤트로 처리할 수 없다. |
| 늘길을 열거나 다시 돌아오면 오늘의 경로 후보가 보인다 | 구현 가능한 PT 기본 경로. [Pleos 앱 동작 모델](https://document.pleos.ai/docs/pleos-only/vehicle-app-planning-guide/app-structure-screen-model)은 전면 복귀·프로세스 재생성에 대비한 앱 자체 상태 복원을 안내한다. 이미 사용한 앱이 창에 다시 나타날 수 있다는 설명은 시동마다 늘길을 여는 보장이 아니다. 등록 규칙·선호·허용된 이력을 읽고 **현재 시간대 기준으로 다시 제안**한다. 이전 추천이나 모의 교통 시간을 오늘의 값으로 재사용하지 않는다. |
| 안내 중이던 순정 내비 상태를 확인한다 | 공개 조회 수단 있음. [NaviHelper 초기화](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/initialization-and-release) 후 [공개 메서드](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/navi-helper/ai.pleos.playground.navi.helper/navi-helper/entry)의 getRouteStateInfo·getDestinationInfo를 사용한다. 상태를 읽은 것만으로 경로를 만들거나 되살렸다고 할 수 없다. 실제 응답과 화면 반영은 미검증이다. |
| 사라진 순정 경로를 자동 복원한다 | 확인한 공개 목록에는 이전 세션의 경로를 복구하는 메서드가 없다. [목적지 가이드](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/destinations)의 requestRoute는 새 목적지 설정이고, [경로 가이드](https://document.pleos.ai/docs/pleos-only/connect-sdk-pleos/NaviHelper/routes)의 requestReRoute는 현재 위치와 목적지 기준 재탐색이다. 앱에 다시 들어왔다는 이유만으로 지난 경로를 재요청하지 않는다. |

## 현재 소스와 차이

프런트 기준 10fdc69의 frontend/README.md와 frontend/docs의 BACKEND_REQUESTS.md, 04_변경안과_결정사항.md, 03_DFD와_시스템구조.md를 읽었다. 18건은 프런트 기록에 있는 로컬 DEMO 연결 검사다. 폰 장면에서 시연 버튼으로 탑승을 재현한 결과는 실제 폰 전송·시동 자동 실행의 증거가 아니다.

백엔드 기준 061feba의 [AndroidManifest.xml](../app/src/main/AndroidManifest.xml)에는 MAIN/LAUNCHER가 있고 부팅 수신기는 없다. [RoutineActivity](../app/src/main/java/kr/routine/app/RoutineActivity.java)는 생성 시 화면과 게이트웨이를 연다. [순정 어댑터](../app/src/main/java/kr/routine/app/platform/PleosNaviGateway.java)의 recoverReadOnly는 **발행 여부가 불확실한 요청**이 있을 때만 저장한 목표를 현재 순정 목적지·좌표·경로 성향·안내 모드와 대조한다. 일치하지 않으면 차단을 유지한다. 이 코드는 지난 이동을 다시 시작하는 기능도, 모든 활성 경로를 화면에 알려 주는 BR-05도 아니다.

## 2026-11-05 사용자 결정 · 폰에서 보낸 경로는 자동 시작

제품 메시지는 **“타면 이미 경로가 돼 있는 차”**로 유지한다. 폰에서 미리 경로를 전송한 행동을 운전자 확인으로 본다. 차량 앱이 열린 뒤 취소할 시간을 주고, 해당 경로가 여전히 유효하면 요청 직전에 `refreshActiveRoute()`로 현재 경로를 다시 읽는다. 새 응답의 `navigation.canConfirm`이 참일 때만 그 이동의 `confirm()`을 한 번 보낸다. 이미 안내 중이거나 조회 실패·정차 미확인·취소 상태면 보내지 않는다. 앱 복귀나 응답 유실 때도 재전송하지 않는다. 폰에서 보내지 않은 날에는 운전자가 차량 화면에서 안내 시작을 누른다. [BR-05 발행 조건](BR05_ACTIVE_ROUTE.md)

시동만으로 차량 앱이 열리는지는 공개 근거가 없어 미검증이다. 영상에서는 운전자가 늘길을 여는 장면으로 시작하고, 폰 전송 장면에는 **“구현 목표 · 폰에서 경로를 보내 두면 차량 앱을 열었을 때 정차와 현재 경로를 확인해 안내를 자동으로 요청합니다.”**라고 표시한다. 웹에서는 폰 전송과 탑승을 모의로 재현한다. 실제 폰 전송과 차량에서의 자동 안내 요청은 구현 목표다. [프런트 결정 기록 9·10장](../frontend/docs/04_변경안과_결정사항.md)
